# 0012. Accounts, sessions, re-auth and API tokens

- Status: Accepted
- Date: 2026-10-28

## Context
steward-ai must be safe on a LAN with no proxy in front (principle 6): a real login,
rate limiting, and nothing reachable without a session or token. It has one owner
account for now, password only. Sensitive steps (locked folders, unlocking, creating
API tokens, changing login settings) need a fresh password check whose window the
owner can change or turn off. Scripts and other programs need tokens that can never
approve AI proposals or reach locked folders.

## Decision
- **Passwords:** argon2id via `argon2-cffi` with its defaults (RFC 9106 low-memory
  profile: t=3, m=64 MiB, p=4); hashes are upgraded on the next login when the
  parameters change. Passwords are NFKC-normalized. Rules: 12-1024 characters, at least
  4 different characters, not on a small built-in common-password list (also after
  removing trailing digits and symbols), not containing the username. At most two
  hashes run at once, so a burst of logins can't exhaust memory. Unknown usernames run a
  dummy verification so timing doesn't reveal which names exist.
- **Usernames** are stored normalized (NFKC, trimmed, case-folded; `[a-z0-9._@-]`,
  1-64 characters).
- **Sessions are server-side.** The cookie holds a 256-bit random secret; `state.db`
  stores only its SHA-256. A session ends after `session_idle_hours` (12) without a
  request or `session_max_days` (7) after login, from `steward.yaml`, checked on every
  request, so changing them applies to existing sessions. `last_seen` is written at most
  once a minute. Ended sessions are kept for `retention_days` (30) for the sessions list.
- **CSRF tokens** are an HMAC of the session secret: nothing extra is stored, and they
  change with the session. The HTTP layer (with `steward api`) checks them on every POST.
- **Re-auth:** a password check (login, re-auth prompt, or password change) stamps
  `sessions.reauth_at`. Settings live in `settings_kv` (`auth.reauth_enabled`,
  `auth.reauth_minutes`, default on / 15). A sensitive step is allowed when the stamp is
  newer than the window. Window `0` means every time: a check allows exactly one
  sensitive step within 2 minutes, then is used up. Turning re-auth off is allowed, with
  a warning in the CLI, the logs and the `core.auth` health check. Changing these
  settings itself needs a recent check. Stored settings that don't validate stop
  re-auth decisions with an error (fail closed) instead of falling back to defaults.
- **API tokens** look like `stw_<43 random characters>`, are stored as SHA-256 with a
  4-character hint, have scopes `read` and/or `propose` and an optional expiry, and are
  revocable. Tokens are created from a session with a recent password check, or by the
  host CLI. A token principal can never re-auth, so everything gated by
  `require_recent_auth` (approvals, locked folders, settings, new tokens, password
  changes) is out of its reach by construction.
- **Rate limiting** is stored in `login_attempts` (so restarts don't reset it) and
  counts failed password checks (logins and re-auth) per client address (default 10)
  and per username across addresses (default 50, higher so one attacker can't easily
  lock the owner out) within 15 minutes after the key's last success. A locked key is
  refused for 15 minutes after its latest failure without checking the password, and
  those refusals aren't recorded, so a lockout can't be extended forever. Failures emit
  `auth.login_failed` (username and address, never the password) and `auth.locked_out`.
- **Client address:** `X-Forwarded-For` is believed only hop by hop from the right while
  each hop is in `trusted_proxies` (`steward.yaml`); with none configured, the connecting
  address is the client.
- **Recovery** happens on the host: `steward user reset-password` (ends all sessions
  and lifts lockouts), `steward user unlock`, `steward user logout`.

## Consequences
- One new runtime dependency (`argon2-cffi`, MIT, with `argon2-cffi-bindings`, `cffi`,
  `pycparser`).
- The HTTP layer (cookies with `HttpOnly`, `Secure` over HTTPS, `SameSite=Strict`, CSRF
  checks, the login and re-auth pages) is built with `steward api` and only calls `Auth`
  (ADR 0013).
- More users later is additive: accounts already carry a `role`; the check constraint
  and `create_owner` are the only places that assume a single owner.
- Someone who controls a trusted proxy, or has shell or disk access, is outside this
  model (documented in the README).
